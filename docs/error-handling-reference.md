# 智简 AI 错误处理 Reference

## 1. 基本原则

1. 后端负责记录内部错误，客户端只接收安全、可理解的错误信息，不返回 SQL、堆栈、密钥或第三方原始响应。
2. HTTP 状态码表示错误类别，响应体中的 `code` 表示业务成功或失败，`data.error_code` 提供稳定的程序判断标识。
3. 页面和组件不直接解析 HTTP 响应，不直接调用 `fetch`，统一通过 `services/request.ts`。
4. Store 不吞掉业务错误；在完成必要的状态清理后继续向上抛出，由触发操作的页面决定展示方式。
5. 同一个错误只提示一次，禁止请求层、Store 和页面重复弹出提示。

## 2. 标准响应

成功：

```json
{
  "code": 0,
  "msg": "success",
  "data": {}
}
```

失败：

```json
{
  "code": 1,
  "msg": "用户可理解的错误信息",
  "data": {
    "error_code": "RESUME_NOT_FOUND"
  }
}
```

## 3. HTTP 状态码

| 状态码 | 使用场景 |
| --- | --- |
| 400 | 参数格式或业务输入不合法 |
| 401 | 未登录、Access/Refresh Token 无效或过期 |
| 403 | 已登录但账号或权限不允许操作 |
| 404 | 当前用户作用域内资源不存在 |
| 409 | 邮箱、用户名等唯一数据冲突 |
| 422 | 数据格式正确但无法完成业务处理 |
| 429 | 请求过于频繁 |
| 500 | 未预期的服务器错误 |
| 503 | 数据库、模型服务等依赖暂时不可用 |

## 4. 前端处理层级

- `services/request.ts`
  - 捕获网络异常并转换为 `ApiError`；
  - 解析 `code/msg/data`；
  - 注入 Access Token；
  - 遇到 401 时单次刷新并重试原请求；
  - 不显示 UI 提示。
- `services/${ModuleName}.ts`
  - 定义语义化接口；
  - 不捕获无法恢复的错误；
  - 不显示 UI 提示。
- `store/${ModuleName}.ts`
  - 使用 `try/finally` 维护 loading；
  - 仅在可恢复时修正本地状态；
  - 错误继续抛给调用页面。
- 页面/组件
  - 表单字段错误使用 Ant Design Form 就地展示；
  - 用户主动操作失败使用 `message.error`；
  - 删除等危险操作使用 Modal 二次确认；
  - 页面首次加载失败使用 Result/Alert，并提供重试入口。

## 5. 错误文案

1. 使用“发生了什么 + 用户下一步可以做什么”，例如“网络连接失败，请检查网络后重试”。
2. 禁止只显示“error”“失败”或内部错误文本。
3. 不把 HTTP 状态码、数据库表名、JWT 解析错误直接展示给用户。
4. 未知错误统一回退到“操作失败，请稍后重试”。

## 6. 稳定错误码命名

- 使用大写蛇形命名：`RESUME_NOT_FOUND`。
- 格式为 `${DOMAIN}_${REASON}`。
- 已发布的错误码不可改变语义。
- 页面只有在确实需要不同交互时才依据错误码分支；普通提示直接使用 `msg`。
